# W5 每日任务卡 · Agent 评测与可观测

> 配套 [[Agent开发学习计划]] 的 **W5（评测与可观测）** 主题执行卡。
> 主题：给 W2–W4 的 Agent 套上**质量护栏**——既能用「LLM-as-judge」自动打分评测，又能用「自建 Tracer / AI SDK telemetry」把一次运行变成可观测的时间线。这是区分「玩具 Demo」与「能上线产品」的分水岭，也是高级岗的加分项。
> 已落地的可运行脚手架：`learning-AI/w5-agent-eval`（Node + `tsx` + `vitest`），可直接 `npm install && npm test` 跑离线单测。

## 周目标（验收总纲）

- [ ] 写一个 LLM-as-judge 评测器：对 Agent 输出按 rubric 打 0–10 分，给出 `passed` + `reasoning`
- [ ] 写一个零依赖自建 Tracer：记录一次运行的 span 时间线（模型 / 工具 / 各阶段），可导出 Markdown 报告
- [ ] 理解 AI SDK 原生 `telemetry` 选项，知道如何接 OpenTelemetry / Langfuse 做生产可观测
- [ ] 用 `vitest` 给工具 + 评测器写**离线单测**（不依赖 API key），养成「改 prompt / 工具即跑回归」的习惯

预计总耗时：12h（约 5 天 × 2.5h）

> 避坑（W5 / AI SDK v7）：`tool.execute` 在 v7 返回联合类型且需第二个 `options` 参数，直接 `.execute()` 不便断言 → 把核心逻辑抽成纯函数（如 `safeCalc` / `searchKnowledge`）再单测；`telemetry` 选项**不支持 `metadata` 字段**，只用 `{ isEnabled, functionId }`，无 OTel SDK 时自动 no-op；`generateObject({ model, schema, system, prompt })` 做结构化评审，`schema` 字段加 `.describe()` 更稳；评测器与 Agent 都做成「可注入」（`runEval(judge, agent, dataset)`），离线单测用 mock、真实跑用 LLM。

## 🗓️ D1 · 评测心智 + 数据集设计

**目标**：搞懂「为什么要评测」，设计可复用的评测数据集。

**任务**
1. 读 [[Agent评估]]：区分两类指标——**确定性指标**（精确匹配 / 关键词 / 正则 / 工具结果是否正确）与 **LLM-as-judge**（用另一个 LLM 评主观维度）。
2. 设计评测用例格式：每条 = `{ id, input, context?, criteria: [{ name, description, weight? }] }`（见 `sample/dataset.json`）。
3. 想清楚你要评什么：本卡评「是否调对工具 / 结果是否正确 / 是否有解释」——按业务挑 2–3 条标准即可。

**验收标准**
- 能口述「评测 = 把『Agent 好不好』变成可量化、可回归的分数」。
- 写得出 ≥2 条带权重的评审标准。

**产出**：评测数据集 `sample/dataset.json`。
**耗时**：2h

---

## 🗓️ D2 · 自建 Tracer（可观测核心）

**目标**：不依赖任何 SaaS，用纯 TS 记录一次 Agent 运行的 span 时间线。

**任务**
1. 读 [[可观测性]]：理解 span = 一个「有开始/结束/耗时、可嵌套」的片段，一次运行 = span 树。
2. 实现 `Tracer`（`src/trace.ts`）：`span(name, fn)` 记录嵌套耗时，`event(name, attrs)` 打时间点，`report()` 导出 Markdown 时间线。
3. 跑 `npm run demo` 看离线效果：应出现 `agent:run → retrieve / tool:calculator / model:generate` 的嵌套时间线。

**验收标准**
- 离线 `npm run demo` 能打印出带父子关系的 span 表格。
- 能口述「自建 Trace 与生产 OTel 是同一套 mental model，只是导出方式不同」。

**产出**：可运行的 `Tracer` + demo。
**耗时**：2.5h

---

## 🗓️ D3 · LLM-as-judge 评测器

**目标**：用 `generateObject` + zod 让 LLM 给 Agent 输出按 rubric 打分。

**任务**
1. 定义 `judgeSchema = z.object({ score: 0-10, passed: bool, reasoning: str })`，用 `generateObject({ model, schema, system, prompt })` 产出。
2. 写 `llmJudge`（真实）与 `JudgeFn` 类型（可注入），让单测能用确定性 mock 替换。
3. 本地 `npm test` 里用 mock judge 验证评分聚合逻辑（无需 key）。

**验收标准**
- 评测器能输出结构化分数 + 是否通过 + 一句理由。
- 能讲清「LLM-as-judge 的优点（评主观维度）与代价（偏差 / 成本）」。

**产出**：`judge.ts`（LLM 评审员）。
**耗时**：2.5h

---

## 🗓️ D4 · 串起来 runEval + AI SDK telemetry

**目标**：把「跑 Agent → 逐条 judge → 聚合 → 写报告」串成一条命令，并接原生可观测。

**任务**
1. 写 `runEval(judge, agent, dataset)`：遍历数据集，每例包成 `eval:<id>` span，逐条 judge，算出加权均分 / 通过率，写出 `eval-report.md`。
2. 在 `agent.ts` 给 `streamText` 加 `telemetry: { isEnabled: true, functionId: 'w5-demo-agent' }`，并把它整体包进 `tracer.span('agent:run')`。
3. 跑 `npm run eval`（需 `.env` 填 key）生成真实评测报告，对照 `npm run demo` 的离线 trace。

**验收标准**
- 一次命令产出「逐例分数 + 通过率 + 加权均分 + trace 时间线」的完整报告。
- 能讲清「AI SDK telemetry 走 OpenTelemetry 标准，有 SDK 才真正导出，没 SDK 自动 no-op」。

**产出**：`runEval.ts` + 真实评测链路。
**耗时**：2.5h

## 🗓️ D5 · 测试 + 回归 + 入库

**目标**：把「评测即回归」固化成习惯，沉淀到 GitHub 与知识库。

**任务**
1. 补齐 `tests/`：`tool.test.ts`（测纯函数核心）+ `eval.test.ts`（注入 mock agent/judge 做离线回归），确保 `npm test` 全绿且不依赖 key。
2. 写一段复盘（≤200 字）：「评测与可观测分别解决什么问题？为什么它们该从 W5 就开始，而不是等上线才补？」
3. `git push` 工程到 GitHub，README 写清「`npm run demo` / `npm test` / `npm run eval`」三步；并在知识库补 [[Agent评估]]、[[可观测性]] 两个实体页（与本卡互链）。

**验收标准**
- [ ] `npm test` 全绿（离线）
- [ ] GitHub 有提交 + README
- [ ] 能讲清「评测 = 质量护栏，可观测 = 排查与信任的前提」

**产出**：W5 作品（GitHub 链接 + 复盘 + KB 实体页）。
**耗时**：2.5h
