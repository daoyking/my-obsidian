# W3 每日任务卡 · RAG 流式问答站

> 配套 [[Agent开发学习计划]] 的 **RAG** 主题执行卡（计划表 W5 行；工程命名为 `w3-rag-qa` 为脚手架序号）。
> 主题：用 [[Vercel-AI-SDK]] 搭一个**检索增强生成（RAG）**问答站——把「检索」封装成工具，模型自主调用 `retrieve` 从本地知识库取回相关片段，再**带引用流式**作答；前端把检索来源（文件名 + 相似度 + 片段）实时可视化。
> 已落地的可运行脚手架：`learning-AI/w3-rag-qa`（Express 后端 + Vite/React 前端，纯内存向量库零外部依赖），可直接 `npm install && npm run dev` 参考。

## 周目标（验收总纲）

- [ ] 本地能跑一个网页问答站，回复**逐字流式**出现且**带引用来源**
- [ ] 模型能**自主调用 `retrieve` 工具**做检索，前端可视化每次检索的「来源清单（文件名/相似度/片段）」
- [ ] 代码 push 到 GitHub，README 写清运行步骤

预计总耗时：12h（约 5 天 × 2.5h）

---

## 🗓️ D1 · RAG 概念 + 最小问答

**目标**：搞懂 RAG 三阶段（Ingest → Retrieve → Generate），跑通一个能发问题的空壳界面。

**任务**
1. 读 [[RAG]] 主题，口述「为什么要检索——模型不知道的知识库外知识，靠检索注入上下文」。
2. 初始化工程：`Vite + React + TypeScript` 前端，`Express + Node` 后端（或直接沿用 `learning-AI/w3-rag-qa`）。
3. 后端先写一个**纯回声**接口：`POST /api/chat` 原样返回用户输入，验证前后端联通。

**验收标准**
- 打开 http://localhost:5174 能看到输入框，发问题后气泡回显。
- 能说清「RAG = 先检索再生成，检索结果以上下文形式喂给模型」。

**产出**：可运行的空壳问答页（GitHub 提交 1 次）。
**耗时**：2.5h

---

## 🗓️ D2 · Ingest（分块 + 向量化）

**目标**：把本地 `docs/*.md` 切成片段，用 embedding 变成向量，存内存。

**任务**
1. 后端引入 `@ai-sdk/openai`，用 `createOpenAI({ baseURL }).embedding(model)` 走 embedding（OpenAI `text-embedding-3-small`）。
2. 写分块函数：按段落/标题切片，每段保留来源文件名。
3. 用 `embedMany({ model, values: chunks })` 批量生成向量，启动期 `ingest()` 加载进内存数组。
4. 用 `node` 单测验证：加载后内存里有 N 条「向量 + 文本 + 来源」，且 embedding 维度正确（如 1536）。

**验收标准**
- 启动日志显示「已索引 N 个片段」。
- 能口述「embedding 把文本变成可比较距离的向量，相似文本距离近」。

**产出**：可索引本地知识库的 ingest 模块。
**耗时**：2.5h

---

## 🗓️ D3 · Retrieve（余弦相似度 + 检索工具）

**目标**：把检索做成工具，模型自主决定何时检索——复用 Agent 循环。

**任务**
1. 写 `cosineSimilarity(a, b)`，对查询向量与全部片段向量算相似度，取 topK。
2. 用 `tool({ description, inputSchema, execute })`（v7 注意 `inputSchema` 不是 `parameters`）定义 `retrieve`，`execute` 内调 `embed` 单条查询向量 + 余弦 topK 返回来源片段。
3. 把 `retrieve` 传给 `streamText`，问「知识库里怎么讲 Agent？」验证模型先调 `retrieve` 再回答。

**验收标准**
- 问知识库内的问题，模型返回的答案来自 `retrieve` 取回的片段而非凭空编。
- 能口述「检索即工具——和 W2 工具调用是同一套循环，只是工具做的是向量检索」。

**产出**：带 `retrieve` 工具的 Agent。
**耗时**：2.5h

---

## 🗓️ D4 · 流式生成 + 来源可视化（前端护城河）

**目标**：把检索来源做成清单卡片，让「模型检索了什么、来自哪篇文档」一眼可见。

**任务**
1. 前端遍历 `message.parts`，遇到 `type` 为 `tool-retrieve`（或 `dynamic-tool`）的片段，渲染一个「来源清单」卡片。
2. 卡片展示：每条来源的文件名、相似度分数、片段预览文本。
3. 打磨样式（暗色主题、来源高亮），让「提问 → 检索 → 带引用流式作答」链路清晰。

**验收标准**
- 问答流里能看到「检索到 3 条来源」卡片，含文件名/相似度/片段。
- 正文里能对应到来源出处（引用感）。

**产出**：带来源可视化的 RAG UI（截图进作品集）。
**耗时**：2.5h

## 🗓️ D5 · 复盘 + 扩展 + 入库

**目标**：巩固 RAG 全链路，加一个增强点，沉淀到 GitHub。

**任务**
1. 自己**加 1 个增强**（任选）：混合检索（BM25 + 向量）、引用高亮、换更大知识库、或把内存向量库换成 Chroma / pgvector / Qdrant。
2. 写一段复盘（≤200 字）：「RAG 三阶段各自解决什么问题？前端在哪一环创造价值？」
3. `git push` 到 GitHub，README 写清「填 key → install → dev」步骤。

**验收标准**
- [ ] ≥1 个自加增强可用
- [ ] GitHub 有提交 + README
- [ ] 能向别人讲清 RAG 全链路

**产出**：W3 作品（GitHub 链接 + 复盘）。
**耗时**：2h
