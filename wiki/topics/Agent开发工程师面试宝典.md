## 0. 先看清战场：面试官要什么

### 0.1 你的三条主线叙事（转型面试的核心武器）

10 年前端转型，面试官最大的疑虑是「你会不会只懂 UI」。你要主动把三个差异化故事讲出来：

| 你的资本 | 翻译成 Agent 语境 | 对应计划 |
|---|---|---|
| 前端工程化：组件、状态管理、工程构建 | **能理解 Agent 的编排、状态、流程**——Workflow/Graph 就是前端的组件树 + 状态机 | W3-W4 |
| 桌面工具制造：WinSnap 的 AX 窗口控制 | **会造「工具（Tools）」**——Agent 的手脚。模型只负责决策，工具质量决定 Agent 上限 | W2-W3 |
| 已消费 Apple 日历/提醒等 MCP | **懂 MCP 协议的消费者视角**，从消费者转生产者路径最短 | W5-W6 |

**参考话术**：「我理解 Agent 的核心是『大模型（大脑）+ 工具（手脚）+ 循环（思考-行动-观察）』。我之前做的窗口管理工具，本质上就是给系统装了一只手——定义清楚输入输出、处理失败、暴露最小能力。转 Agent 开发后，我发现这套工具工程化的经验可以直接复用，我缺的只是大脑部分，也就是对 LLM 和协议的理解，这个我正在系统补。」

### 0.2 面试官最可能的三个质疑与应对

1. **「你没有大模型开发经验」** → 承认 + 给出学习证据：手写 ReAct 循环、自建 MCP Server、验收项目（W3/W6/W10 的产出就是证据）。不要空谈「我学得快」。
2. **「前端来做 Agent 是不是降维」** → 不否认前端是存量技能，强调它是增量：Agent 产品最终要落到 UI 交互，前端的产物、状态、异步、错误处理思维是 Agent 工程的同构能力。
3. **「你为什么要转型」** → 讲「能力迁移」而不是「前端没前途」：10 年工程经验的判断力 + AI 自动化方向是新杠杆。切忌踩旧行业。

## 1. LLM 基础（必考，答好开场的定盘星）

### 1.1 什么是大语言模型？

**考察点**：面试官想确认你不是只会调 API，而是理解本质。

**参考回答**：「大语言模型是基于 Transformer 架构、在海量文本上做『下一个词预测』预训练出来的概率模型。它学习的是语言的统计规律和世界知识，通过自回归逐词生成输出。它的核心能力是『续写』，Agent 应用做的，是给这个续写器设计好上下文和工具，让它完成特定任务。」

**追问防御**：别把「概率模型」说成「什么都不知道」——要用「知识压缩在参数里，可能过时或缺失」来过渡到幻觉问题。

### 1.2 Token 是什么？上下文窗口越大越好吗？

**考察点**：成本意识 + 上下文工程意识。

**参考回答**：「Token 是模型处理文本的最小单位，中文大约 1 个汉字 ≈ 1-2 个 Token，1K Token 约等于 500-700 个汉字，输入输出都按 Token 计费。上下文窗口是模型一次能看到的 Token 上限。窗口不是越大越好——窗口越大，成本越高、推理越慢，而且模型对长上下文中间部分的『注意力』会衰减（业界叫 lost in the middle），更重要的是，塞太多无关内容会稀释关键指令。」

**参考话术**：「所以我做上下文管理时有个原则：能用检索解决的问题，不靠把全文塞进去解决；能压缩的（历史摘要）先压缩。」

### 1.3 system / user / assistant 三角色

**考察点**：API 基本功。

**参考回答**：「system 定义模型的身份和行为准则，优先级最高，是『守门人』；user 是用户的输入；assistant 是模型的历史回复，用来维持多轮对话的连续性。Agent 场景里，工具调用结果通常以 tool 消息（或伪 assistant 消息）回填，让模型知道『动作已执行、结果是啥』。」

### 1.4 temperature / top_p / max_tokens 是什么？

**考察点**：参数理解 + 场景选择。

**参考回答**：「temperature 控制输出随机性：越低越确定（适合抽取、分类、代码生成），越高越发散（适合创意文案）；top_p 是核采样，按累积概率截断候选词，和 temperature 二选一调即可；max_tokens 限制输出长度。工具调用场景建议低 temperature，避免模型编造参数。」

### 1.5 什么是幻觉？为什么会有？怎么缓解？

**考察点**：AI 应用开发最基本的风险意识。

**参考回答**：「幻觉是模型生成『看似合理但事实上错误或不存在』的内容。原因是：预训练目标是『像人一样续写』而不是『保证事实正确』，知识有截止日期、参数容量有限，且模型天然倾向迎合用户的提示。缓解手段从轻到重：一是提示层面（要求引用来源、不确定就承认）；二是检索增强 RAG，把事实锚定在检索结果上；三是系统层面（工具返回真实数据、后置校验、关键数字用代码计算而不是让模型算）。」

### 1.6 结构化输出怎么保证？

**考察点**：工程落地能力——所有 Agent 都建立在结构化输出上。

**参考回答**：「三层手段：第一，提示词里给 JSON 格式示例（few-shot）；第二，用 JSON mode / 响应格式参数强制模型输出合法 JSON；第三，函数调用（Function Calling）——模型不是返回自由文本，而是返回带工具名和参数的结构化调用，schema 由我们定义。生产环境我还会做一层解析容错：模型偶尔返回带 ```json 围栏或多余文字，解析失败时让模型重试或修正。」

### 1.7 流式输出（SSE）和普通输出的区别？

**参考回答**：「普通请求等模型生成完一次性返回，首字延迟高；流式用 SSE 把 token 逐个/分批推给前端，首字快、体验好。代价是后端要做事件流处理、中断处理（用户停止生成时要能取消上游请求）。前端对这个最熟——就是长连接 + 事件流。」

**参考话术**：「这块其实是前端的老本行，SSE/WebSocket 我之前天天用，转型后直接平移。」

## 2. Prompt 工程（必考）

### 2.1 写好 prompt 的要素

**考察点**：是否把 prompt 当「可维护的工程资产」而非玄学。

**参考回答**：「五个要素：角色（你是谁）、任务（做什么）、上下文（已知信息）、示例（few-shot，最有效的约束）、输出格式（结构/长度/风格）。好的 prompt 是可测试的——改变一个变量能观察效果，所以生产环境我会把 prompt 版本化管理，和代码一起发版。」

### 2.2 Zero-shot / Few-shot / CoT 是什么？

**参考回答**：「Zero-shot 是直接提问；Few-shot 给 2-5 个输入输出示例，让模型模仿格式和推理路径，是最便宜的『对齐手段』；CoT（思维链）让模型先推理再回答，显著提升数学、逻辑类任务准确率——本质是给模型『思考的空间』，顺带把推理过程暴露出来方便调试。」

### 2.3 什么是 Prompt 注入？怎么防御？

**考察点**：安全意识——Agent 有工具后注入风险陡增。

**参考回答**：「Prompt 注入是攻击者把恶意指令藏在用户输入或外部内容（网页、文档、邮件）里，试图覆盖 system 指令，让 Agent 执行未授权操作。防御分层：输入侧做指令边界（把外部内容隔离、标注为『数据』而非『指令』）、输出侧做工具白名单、高危操作（删除、发消息、转账）强制人工确认、敏感操作要求二次验证。核心原则是：**永远不要信任模型对外部内容的解读**，工具权限要最小化。」

> 深入见 [[提示注入]] 与 [[Agent安全]]。

## 3. Agent 核心机制（重中之重，转型岗必考）

### 3.1 什么是 Agent？和普通 LLM 应用、Workflow 的区别？

**考察点**：Agent 与 Workflow 的区分是 2026 年面试最高频题之一。

**参考回答**：「普通 LLM 应用是一次『问答』：输入 → 模型 → 输出。Workflow 是预定义好的流程：节点固定，LLM 只是其中一个执行者。Agent 则把『决策权』交给模型——它自己决定下一步调用什么工具、要不要继续，是一个『思考-行动-观察』的动态循环。一句话：Workflow 是写死的剧本，Agent 是让模型临场发挥。工程上常把两者结合：确定的部分用 Workflow 固化，不确定的部分用 Agent 兜底。」

**参考话术**：「我个人的理解：Workflow 的流程图是开发时画好的，Agent 的流程图是运行时模型自己画的。」

### 3.2 Function Calling 的原理是什么？（必考）

**考察点**：是否真懂而不是背概念。

**参考回答**：「Function Calling 的本质是：我们把工具定义（名字、参数 schema、描述）随对话一起发给模型，模型判断『这个问题需要调用工具』时，不直接输出答案，而是输出一个结构化的 tool_call（工具名 + 参数 JSON）。**模型自己不执行任何函数**——我们的代码负责执行，把真实结果以 tool 消息回填给模型，模型再基于结果继续回答或再次调用。整个过程通常 2-3 轮。支持并行调用时多个 tool_call 一次返回，可以显著省时间：串行是 T1+T2+T3，并行是 max(T1,T2,T3)。」

**参考话术**：「它不是魔法，就是『模型输出一段结构化 JSON，我执行，把结果塞回对话』。我学习时亲手写过这个流程，几十行代码就跑通了。」

### 3.3 手写 Agent 循环：ReAct（必考）

**考察点**：2026 年面试官默认候选人读过 ReAct。你答得越具体越加分。

**参考回答**：「ReAct 是 Agent 最基础的模式：循环执行 思考（Thought，分析现状、决定下一步）→ 行动（Action，调用工具）→ 观察（Observation，看工具结果），直到模型认为任务完成。工程实现要点：维护一个消息列表，把 thought/action 以函数调用形式发出、把 observation 回填；必须设置最大迭代步数；处理三类失败——工具报错（把错误信息回填让模型改方案）、超步数（截断并总结已做内容）、模型输出畸形 JSON（提示重试或修正格式）。」

> 深入见 [[ReAct]]。你的 [[Agent开发学习计划-Python路线]] W3 要求 80 行手写循环——做完那个产出，这道题你就能碾压大多数候选人。

### 3.4 如何防止 Agent 死循环？

**参考回答**：「四道防线：最大步数上限（最常见，配超时）；重复动作检测（同一工具+相同参数连续 N 次 → 强制停止或换策略）；工具结果去重与缓存；任务目标拆解（把大任务拆成子任务，每个子任务有独立完成判据）。生产环境还要有全局超时和人工中断通道。」

### 3.5 Agent 的记忆怎么设计？

**考察点**：[[记忆系统]] 是高频追问点。

**参考回答**：「分三层：**短期记忆** = 当前对话的上下文窗口，直接拼进 messages；**长期记忆** = 跨会话的用户偏好、事实，存数据库，需要时检索注入；**工作记忆** = 任务执行中的中间状态（已完成步骤、临时变量），通常用结构化的状态对象维护。关键工程点是上下文管理：会话太长要摘要压缩、选择性遗忘——不是所有历史都该留在窗口里，要按相关性检索注入。」

**参考话术**：「我做过一个『会话记忆』实验：用 JSON/sqlite 存历史，超长时自动摘要，重启后还能记住用户偏好。向量检索是进阶，用来做语义级记忆召回。」

### 3.6 多 Agent 协作

**参考回答**：「两种模式：**编排式**（Orchestrator-Workers）——一个主 Agent 拆任务、分发给多个子 Agent、汇总结果；**协作式**——多个 Agent 平等对话（如辩论、评审）。框架里 LangGraph 的多节点图就是为此设计的。注意：多 Agent 不是银弹，通信成本高、错误会放大，能用单 Agent 解决的问题别硬上多 Agent。」

### 3.7 工具调用失败怎么降级？

**考察点**：可靠性意识（W9 的核心）。

**参考回答**：「三层降级：工具层——重试 + 指数退避（限流/超时场景）；Agent 层——把错误信息回填给模型，让它换参数、换工具或明确告知用户失败；产品层——兜底 fallback（降级到无工具纯问答、切换备用模型、人工转接）。可观测是关键：每次工具调用的输入输出、耗时、token 都要有日志，失败才能复盘。」

## 4. MCP 协议（你的差异化赛道，重点）

> MCP（Model Context Protocol）2026 年已是事实标准，国内已落地国家标准。这是你从「消费者」转「生产者」能讲出彩的部分。

### 4.1 MCP 解决什么问题？（必考）

**考察点**：理解协议的价值，而不只是名词。

**参考回答**：「MCP 解决的是『N×M 集成爆炸』：N 个 AI 应用 × M 个工具源，传统方式每个应用都要为每个工具写专属适配，成本是 N×M；MCP 让工具提供方只写一次 Server，任何支持 MCP 的客户端（Claude、千问办公、自研应用）都能即插即用，成本降到 N+M。类比：它是 Agent 世界的 USB-C 接口——工具侧和宿主侧解耦。」

**参考话术**：「我自己就在用 Apple 日历、提醒事项的 MCP，从用户视角看是『装上就能用』；转去读协议后发现，这背后就是一套标准化的工具发现和调用机制。」

### 4.2 MCP 三大原语：Tools / Resources / Prompts

**参考回答**：「Tools 是可执行动作（读写文件、发消息），由模型决策调用，带输入输出 schema，这是 Agent 最常用的一类；Resources 是只读数据（文件内容、数据库记录），按 URI 暴露，供模型按需读取；Prompts 是预置的提示模板，复用复杂指令。三者的分工：Tools 动手、Resources 提供上下文、Prompts 提供工作方法。」

### 4.3 MCP 架构细节

**参考回答**：「架构分 Host（宿主应用）、Client（客户端，每个会话一个）、Server（工具提供方）。传输层：本地用 stdio（子进程管道），远程用 HTTP + SSE 或 Streamable HTTP。消息基于 JSON-RPC 2.0。生命周期：initialize（握手、能力协商）→ tools/list（工具发现）→ tools/call（调用）。SDK 层面用 FastMCP 装饰器几行就能暴露一个工具。」

### 4.4 MCP vs Function Calling vs 普通 API？

**考察点**：三者关系是 2026 高频辨析题。

**参考回答**：「Function Calling 是模型侧的『决策机制』——模型怎么决定调工具、以什么格式输出调用；MCP 是工具侧的『接入标准』——工具怎么被发现、怎么被调用。两者是不同层面：一个 Agent 可以既用 Function Calling 做决策，又通过 MCP 拿工具。普通 API 是一次性硬编码集成，MCP 是标准化即插即用。实际工程里：用 MCP 统一接入工具，用 Function Calling 驱动模型选工具，各司其职。」

### 4.5 生产级 MCP Server 怎么设计？（加分）

**考察点**：安全性 + 工程规范。

**参考回答**：「六个要点：**权限最小化**——每个工具只暴露必要能力，危险操作（删除、覆盖、联网发送）默认拒绝或人工确认；**输入校验**——参数严格校验，防止把用户输入直接拼进 shell/文件路径；**白名单**——可执行命令、可访问路径都要白名单；**审计日志**——记录每次调用来源、参数、结果；**工具描述质量**——描述写得越清楚模型调用越准，这是可以迭代优化的；**幂等与重试**——写操作要有幂等设计，失败要返回结构化错误。」

### 4.6 A2A 协议是什么？和 MCP 什么关系？

**考察点**：2026 新趋势，了解即可，答出来是加分项。

**参考回答**：「A2A（Agent-to-Agent）是 Google 牵头的 Agent 间通信协议，解决『Agent 之间怎么互相发现、委托任务』；MCP 解决『Agent 怎么用工具』。两者互补：MCP 是 Agent 的手脚接口，A2A 是 Agent 之间的社交协议。A2A 目前还在早期阶段，生态快速发展，但底层逻辑不变——工具调用、标准化接入、Agent 协作、安全可靠性是长期核心。」

## 5. 框架与工程化

### 5.1 主流框架怎么选？

**考察点**：是否跟过 2026 生态，有没有亲手对比。

**参考回答**：「三个主流方向：**OpenAI Agents SDK**——轻量、上手快，适合单 Agent 快速落地；**LangGraph**——状态机图模型，适合多 Agent、复杂流程，灵活但重，有学习曲线；**CrewAI**——角色化多 Agent 协作，声明式配置，适合固定剧本的团队协作场景。我的选择原则：先手写一遍循环理解本质，再引入框架——框架替你做的（重试、追踪、循环管理）是送的，但你要知道它限制了什么。」

### 5.2 手写 Agent 循环 vs 框架？

**参考回答**：「手写适合学习、简单场景、深度定制；框架适合生产、复杂编排、需要可视化追踪。我的建议是两手都练：手写保底理解，框架提效落地。面试时能讲『我用 80 行手写过循环，再用 LangGraph 重写，对比了差异』——这比只背框架概念有说服力得多。」

### 5.3 Agent 工程化：日志、可观测、成本（W9 核心）

**考察点**：从「能跑」到「敢用」的距离感。

**参考回答**：「可观测三件套：请求日志（每次 LLM 调用和工具调用的输入输出、耗时、token）、链路追踪（一个任务从开始到结束的完整调用链）、评测（同一批测试集跑回归，验证 prompt/工具改动没引入退化）。成本控制：token 计数、单任务成本估算、月预算告警、模型路由（简单任务用便宜小模型，复杂任务才用强模型）、缓存与摘要压缩。」

## 6. RAG（高频）

### 6.1 RAG 是什么？完整流程？

**考察点**：最经典的 AI 应用工程题，必答。

**参考回答**：「RAG = 检索增强生成。流程五步：**分块（Chunking）**——把文档切成合适大小的块（一般 200-1000 token，带重叠）；**嵌入（Embedding）**——每块转成向量；**向量检索**——查询向量化后在向量库（pgvector/chroma/milvus）里找最相似 Top-K；**重排（Rerank）**——精排模型对初检结果打分，提升准确率；**生成**——把检索结果作为上下文拼进 prompt，让模型基于事实回答并引用来源。进阶：混合检索（向量 + 关键词 BM25）、Query 改写（把用户问题改写成检索友好形式）。」

### 6.2 为什么用 RAG 而不是微调？

**考察点**：两者边界。

**参考回答**：「RAG 解决『知识获取』：知识频繁更新、需要溯源、覆盖面大时用它，成本低、可解释（能指出处）、可随时替换知识源；微调解决『能力与风格』：改变模型的行为模式（格式、语气、领域术语、工具使用习惯），成本高、知识会过时。实践原则：知识问题先 RAG，行为问题才考虑微调。RAG 的短板是检索质量不稳定（召回不准），所以 Rerank 和评测很重要。」

### 6.3 Agentic RAG 是什么？

**参考回答**：「传统 RAG 是一次『检索-生成』的固定管线；Agentic RAG 让 Agent 自己决定检索策略——先检什么、不够再补检、多路检索后综合、检索不到时改写问题再试。把『检索』从被动步骤变成主动工具，本质是 RAG 和 Agent 的融合：RAG 是 Agent 工具箱里的知识查询器。」

### 6.4 如何设计一个企业级知识库问答系统？（系统设计）

**参考回答**：「分四层：**数据层**——多格式文档接入（PDF/Word/网页）、增量更新、权限打标（不同人只能检索到有权限的内容，这是企业场景最容易漏的）；**检索层**——混合检索 + Rerank + 查询改写，评测集定期回归（Recall@K）；**生成层**——prompt 约束『只能基于检索结果回答、不能编造、答不出就明说』，输出带引用；**运营层**——日志 + 用户反馈闭环（badcase 回流优化 chunk 和 prompt）+ 成本监控。」

## 8. 系统设计题（场景题）

### 8.1 设计一个客服 Agent

**考察点**：综合能力——从需求到架构。

**参考回答**：「需求分层：FAQ 类（高频、确定性）→ 工单类（需查系统数据）→ 人工转接（复杂/投诉）。架构：入口（多渠道）→ 意图识别/路由（简单问题用便宜小模型分类）→ 知识检索（RAG，企业知识库）→ 工具调用（查订单、查物流等，走 MCP）→ 兜底（转人工）。可靠性：答案必须基于知识库（防幻觉），不确定就转人工；情绪识别（投诉类直接转人工）。评测：准确率、转人工率、用户满意度。成本：分类用小模型、生成用中模型、复杂推理才用强模型。」

### 8.2 设计一个生产级 Agent 平台

**考察点**：2026 大厂高频系统设计题。

**参考回答**：「关键模块：**模型网关**——多模型路由、限流熔断降级、token 成本归因；**Prompt 管理**——版本化、灰度发布、A/B 测试；**工具注册中心**——MCP Server 统一接入、权限隔离、审计日志；**任务编排**——Workflow 引擎 + Agent 循环支持；**可观测**——全链路追踪、badcase 回放；**评测体系**——回归测试集、质量看板；**安全合规**——敏感数据脱敏、操作留痕、权限模型。」

### 8.3 成本控制怎么做？

**参考回答**：「四板斧：**模型路由**——简单任务小模型（分类/摘要/提取），复杂任务强模型；**上下文瘦身**——只注入必要内容，历史摘要化，检索 Top-K 精而非多；**缓存**——相同/相似请求命中缓存（精确缓存 + 语义缓存）；**预算治理**——按用户/功能/团队做 token 归因，设月度预算告警，超限自动降级。个人工具的话我给自己定的标准是一个月成本 < 30 元——成本意识要变成肌肉记忆。」

## 附：考前 30 分钟一句话速记卡

- **Agent = 大模型（大脑）+ 工具（手脚）+ 循环（思考-行动-观察）**
- **Function Calling**：模型只决策、不执行；输出结构化 JSON；结果回填继续
- **ReAct**：Thought → Action → Observation；防死循环 = 最大步数 + 重复检测 + 超时
- **MCP**：解决 N×M → N+M；三大原语 Tools/Resources/Prompts；stdio 本地 / HTTP 远程；JSON-RPC 2.0
- **MCP vs FC**：FC 是决策机制（模型侧），MCP 是接入标准（工具侧）
- **RAG 五步**：分块 → 嵌入 → 向量检索 → Rerank → 生成；RAG 补知识，微调改行为
- **Workflow vs Agent**：写死的剧本 vs 模型自己画流程图
- **幻觉三板斧**：要求引用 / RAG 锚定 / 关键数字用代码算
- **成本四板斧**：模型路由 / 上下文瘦身 / 缓存 / 预算归因
- **安全三红线**：外部内容当数据不当指令 / 工具白名单最小权限 / 高危操作人工确认
- **你的差异化**：前端工程思维 + 工具制造能力（WinSnap/AX）+ MCP 消费者经验 + 双栈路线
