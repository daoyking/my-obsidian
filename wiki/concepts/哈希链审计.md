# 哈希链审计（Hash-Chained Audit Trail）

## 定义

把 Agent 的每一个动作记成一条日志，每条日志的哈希值由「自身内容 + 上一条的哈希」共同计算得出，形成单向链。改动任何一条，其后所有哈希全部失效——**篡改会留下痕迹，而不是无法篡改**。

配套机制是**信任门控（Trust Gating）**：Agent 参与任务前先过一道评分门槛，分数不够直接拦下，不进入流水线。两者合起来回答多智能体系统的两个问题：**事前**谁有资格干活，**事后**怎么还原发生了什么。

## 来源样例

[[awesome-llm-apps]] 的 `trust_gated_agent_team`（Researcher → Analyst → Writer 三段流水线）。完整机制见 [[raw/articles/awesome-llm-apps-trust-gated-team]]。

## 机制拆解

### 哈希链：每条记录算什么

```
hash_n = SHA256( seq | timestamp | agent | action | input_hash | output_hash | trust_score | hash_(n-1) )
```

创世记录的 `prev_hash` 是全零。导出成 JSON 后，**任何人用 SHA-256 就能独立验证整条链**，不需要信任审计方，不需要特殊工具。

### 信任门控：三段判定

1. **Trust Check** — Agent 分数与最低阈值比较
2. **Gate** — 低于阈值直接拦下，不进入流水线
3. **Execute** — 通过的 Agent 顺序执行，后一个基于前一个的输出
4. **Audit** — 每个动作（**包括信任检查本身**）都进哈希链

第 4 点是设计上最讲究的地方：**被拦下的 Agent 也会留下记录**。否则「谁被拦了、为什么」这件事本身就成了黑箱，审计链会出现缺口。

## 关键：它保证什么，不保证什么

这是最容易被误读的部分。哈希链是 **tamper-evident（篡改可察）**，不是 **tamper-proof（篡改不可行）**。

### ✅ 保证

| 保证 | 机制 |
|---|---|
| 改动任意一条会被发现 | 后续所有 hash 断裂 |
| 删除中间记录会被发现 | 前后 prev_hash 对不上 |
| 顺序无法重排 | seq + prev_hash 构成单向依赖 |
| 可独立验证 | 只需 SHA-256，无需信任审计方 |

### ❌ 不保证（四点，每一条都很致命）

**1. 不保证内容是真的——只保证没被改过。**

日志记的是 Agent **自报**的输入输出。Agent 幻觉了、被 [[提示注入]] 了、工具返回了脏数据——哈希链会**忠实地、不可篡改地记录下这个错误**。它证明的是"这段记录自生成以来没动过"，不是"这段记录描述的事情确实发生了"。

> 类比：监控摄像头拍到某人进了房间。哈希链保证录像没被剪辑，不保证那个人没撒谎说自己去了别处。

**2. 不防整链重造。**

算法完全公开、没有数字签名。任何能接触写入端的人都可以截断链条、重算后面全部哈希，得到一条**内部自洽但内容全新**的链。它防的是"偷偷改一条"，防不住"推倒重来"。

**3. 不防尾部截断。**

删掉最后 N 条，剩下的链依然自洽——因为没有后续记录来暴露断裂。**必须配合外部锚定**（定期把链头哈希写到不可篡改的外部位置）才能堵住这个口子。

**4. 不提供不可否认性。**

没有签名，就无法证明"这条记录确实是 Agent X 产生的"，还是审计方自己伪造的。要真正防抵赖，需要非对称签名 + 可信时间戳。

## 与相邻机制的对比

| 机制 | 防什么 | 不防什么 | 关系 |
|---|---|---|---|
| **哈希链** | 事后悄悄改单条记录 | 整链重造、尾部截断、内容造假 | 本文主角，**动作序列**的完整性 |
| **数字签名** | 抵赖（谁干的） | 内容本身真假 | 与哈希链**互补**，应叠加使用 |
| **[C2PA]** | 媒体内容的来源与编辑史 | 拍摄当时的真实性 | 管**内容**，哈希链管**行为**，可组合 |
| **区块链** | 分布式环境下的整链重造 | 上链前的数据造假 | 哈希链 + 共识 + 经济成本，重得多 |
| **普通日志** | 无 | 一切 | 基线，改了没人知道 |
| **可观测性 trace** | 无（靠平台权限） | 有写权限的人改 | 关注**性能与调试**，不关注**不可篡改性** |

**结论**：哈希链处在「比普通日志强很多、比区块链轻很多」的甜点位。对单组织内部的 Agent 系统，它是性价比最高的选择——**但必须叠加签名或外部锚定才算完整**。

## 信任门控的真正难题：分数从哪来

这是整个机制里**最薄弱的一环**，而样例的 README 完全回避了它。

样例里分数是预置的：Researcher 75 / Analyst 60 / Report Writer 45 / Untrusted Bot 5。README 没说：

- 分数**谁打的**？
- 依据什么**算的**？历史成功率？人工评级？自评？
- **多久更新**？被拦下的 Agent 怎么申诉、怎么翻身？
- 阈值 45 和 60 的差别，凭什么？

**门控的强度 = 最弱的评分环节。** 如果评分是拍脑袋给的，那整套密码学机制只是在严谨地执行一个随意的决定——[[Agent评估]] 里讲的"指标污染"问题在这里会原样重演。

一个可信的门控至少需要三条：

1. **评分依据可审计** — 分数必须能追溯到具体评估基准（见 [[基准测试]]），而不是一个魔法数字
2. **评分动态更新** — 每次任务结果回流调整分数，而非一次性设定
3. **评分本身进审计链** — 分数的每一次变动都要有记录，否则分数是新的攻击面

## 一个被低估的正确设计：外部存储

README 里有一句很容易滑过去的话，但它是整个方案里**最关键的一条**：

> stored externally, not in the agent's own memory

**如果被审计对象能修改自己的日志，任何密码学都没用。** 这条原则比哈希链本身更重要——它决定了整套机制是审计还是装饰。落地时必须保证：

- 日志写入位置 Agent **无写权限**（只有 append 权限，甚至只有独立的写进程能碰）
- Agent 无法读取/枚举自己的历史日志（否则可以针对性地构造"看起来一致"的行为）

## 落地到我的栈

| 场景 | 怎么用 | 优先级 |
|---|---|---|
| **W5 可观测性 trace** | 每个 span 加 `prev_hash` 字段，导出 JSON 即成为可验证链。成本极低（每次一个 SHA-256），收益是 trace 从"调试用"升级为"审计用" | 高 |
| **WorkBuddy 4 人团队 SOP** | QA 门禁已经是门控雏形，但通过/不通过是**二值**的。可升级为评分制（如架构合规度 / 测试覆盖率 / 回归数），并把评分变动记入链 | 中 |
| **[[人机协同]] 的审批动作** | 人类批准/驳回是最高价值的审计事件——它证明"有人看过"。必须进链且带签名 | 高 |
| **[[Coding-Agent]] 的代码改动** | 每次文件变更记入链，配合 git 本身的 commit hash（git 已经是哈希链！） | 中 |

**一个现成的洞察**：**git 本身就是一条哈希链**。每个 commit 包含 parent hash，改动任一历史 commit 会导致后续所有 hash 变化。理解了这一点，哈希链审计就没有神秘感了——它就是把 git 的思路搬到 Agent 行为日志上。

## 工程成本的真实分布

- **哈希计算本身：几乎免费**（SHA-256，微秒级）
- **真正的成本在 `input_hash` / `output_hash`**：长文本要先做**规范化**（空白、换行、字段顺序、时间戳精度），否则同样的内容两次哈希不一样，验证永远对不上
- **规范化规则的制定，比哈希算法难一个数量级**——这是落地时最容易低估的地方

## 我的观点

1. **这个项目真正的价值不在哈希链，在它把两个问题摆到了一起。** 多智能体系统的"事前信任"和"事后追责"平时各说各话，这个样例用不到 200 行把它们串成了一条流水线。这个 framing 比实现更有参考价值
2. **但它是演示级，不是生产级。** 目录下的文件只有 3 个（README / requirements / 单文件 py），无测试、无签名、无外部锚定、分数硬编码。它的正确用法是**当作机制说明书读，而不是当作可抄的代码**
3. **"哈希链防篡改"这个说法有害。** 它让很多人以为上了哈希链日志就可信了。准确的说法是"哈希链让篡改必须付出重算全链的代价，且在有外部锚定的前提下可被发现"——**没有外部锚定的哈希链，安全收益接近零**
4. **信任门控的评分问题是真问题，不是吹毛求疵。** 整个领域（不止这个样例）都在回避"Agent 的可信度到底怎么量化"。在评分机制成熟之前，任何 trust gating 都只是把信任从 Agent 转移到了评分者身上——**信任没有消失，只是换了个地方**
5. **对求职 portfolio 的性价比判断**：实现一套带签名 + 外部锚定的 Agent 审计链，工程量约 2-3 天，但能讲出的深度（密码学取舍 + 威胁建模 + 工程规范化）远超同等工作量的功能开发。**这是 [[Agent安全]] 领域为数不多"小而深"的选题**

## 待研究问题

- [ ] 外部锚定的最轻实现是什么？定期把链头哈希推到公开 git 仓库够不够？还是需要 TSA（时间戳权威）？
- [ ] Agent 行为日志的规范化规则有没有事实标准？（类比 SBOM、SLSA provenance）
- [ ] 「内容真实性」问题怎么解？能否让工具返回值自带签名（如 MCP server 对自己的响应签名），从而把可信边界从 Agent 下移到工具？
- [ ] 信任评分的最小可行方案：基于历史任务成功率的滚动评分，在样本量多少时才稳定？
- [ ] git 作为哈希链的现成能力，能否直接复用（如把 Agent 行为日志写进一个专用 git 仓库）？还是必须独立实现？
- [ ] 尾部截断攻击在没有外部锚定时，有无其他检测手段？（如 seq 上界承诺）
