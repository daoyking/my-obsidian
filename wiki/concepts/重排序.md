# 重排序（Reranking）

## 定义

两阶段检索的第二阶段。**初检索**（快而糙：向量相似度 / BM25）召回较大的候选集（top-50~100），**重排序**（慢而准：交叉编码器）对候选集精排，输出最终 top-5~10 送入生成。

## 为什么必须两阶段，不能直接精排

| | 初检索（Bi-encoder） | 重排序（Cross-encoder） |
|---|---|---|
| 计算方式 | query 与 doc **分别**编码成向量，算余弦 | query 与 doc **拼接**后一起过模型 |
| 能否预计算 | ✅ 文档向量可离线算好，建索引 | ❌ 每次查询都要重新算 |
| 精度 | 中 | 高 |
| 复杂度 | O(1) 检索 | O(N) per query |

直接对全库跑交叉编码器是 O(N)——库一大就不可行。所以必须先用便宜的方式把 N 缩到 50，再用贵的方式精排。**这是检索系统里最经典的「漏斗」结构。**

## 常用模型

- `bge-reranker-v2-m3`（ multilingual，中文友好）
- ` Cohere Rerank`（商业 API，效果强）
- `bge-reranker-base / large`

`contextualai_rag_agent` 样例把 rerank 作为托管能力直接提供，还支持按「自定义指令 + 查询相关性」重排（多语言）。

## 工程取舍（关键）

**重排序是 RAG 管线里最容易踩的延迟坑。**

- CPU 上跑 `bge-reranker`，单查询 50 个候选可能 >2s——直接吃掉整个交互延迟预算
- 有 GPU / Apple Silicon 的 Neural Engine 时可显著加速
- 候选集大小是核心旋钮：top-50 降到 top-20，延迟减半，精度损失通常 <3%（**这条必须自己实测，别信经验值**）

**我的切法**（见 [[RAG实验路线]]）：
- **评测跑批** → 本地跑重排序，慢无所谓，反正批跑
- **线上交互** → 云端 rerank API 或干脆降级为「混合检索 + 无重排序」，用 [[上下文工程]] 里的片段压缩补偿

## 怎么判断该不该上重排序

先测这个：在评测集上对比「混合检索 top-5」vs「混合检索 top-50 + rerank top-5」的 Recall@5。

- 提升 <5pp → 不值得这个延迟，省掉
- 提升 10-20pp → 上
- 提升 >20pp → 说明初检索质量太差，应该先修分块/嵌入，而不是靠 rerank 兜底
