# 知识图谱（Knowledge Graph / Graph RAG）

## 定义

把知识存成「实体—关系—实体」的三元组网络，而非扁平文本块。检索时在图上遍历路径，而不是在向量空间里找最近邻。

## 与向量 RAG 的本质差异

| | 向量 RAG | 图谱 RAG |
|---|---|---|
| 知识表示 | 文本块 + 嵌入向量 | 实体 + 关系边 |
| 检索方式 | 语义相似度 | 图上路径遍历 |
| 擅长 | 「这段话在讲什么」 | 「A 和 B 通过什么关联」 |
| 多跳推理 | 弱（每跳都要重新检索，误差累积） | 强（路径天然是多跳的） |
| 可验证性 | 引用到 chunk | 引用到具体节点与边 |
| 构建成本 | 低（分块+嵌入） | 高（需实体关系抽取） |

## 什么时候值得上图谱

判据很简单：**你的问题里有多少是「关系型」的？**

- 「这份文档讲了哪些产品」→ 向量 RAG 就够
- 「张三参与的项目里，哪些用了 Rust」→ 需要跨实体关联，图谱优势明显

`knowledge_graph_rag_citations` 样例的定位很准确：传统向量 RAG 在「需要跨多文档」「复杂推理链」「每条断言都要可验证来源」这三件事上吃力，图谱正好补上。

## 工程现实

**图谱的瓶颈不在查询，在构建。** 实体关系抽取的质量决定一切：

- 用大模型抽（GPT-4 / Claude）：质量高，成本随文档量线性增长
- 用本地小模型抽（`qwen3:8b` 级）：便宜，但关系错抽、漏抽严重——这是 [[RAG实验路线]] Stage 4 的待研究问题
- 用规则/正则抽：只在结构化程度高的语料上可行

**轻量替代**：不一定非要上 Neo4j。做成千上万个节点的规模，内存图（如 `networkx` 或 JS 侧的图结构）完全够用，还省掉一整套运维。

## 与 LLM Wiki 的关系

本知识库（[[CLAUDE]]）的 `wiki/` 层用双链构成的知识网络，**本质上已经是一张手工编织的知识图谱**——只不过节点是人类可读的笔记页，而非三元组。

这个观察有实操价值：[[RAG实验路线]] Stage 4 做图谱实验时，vault 的双链结构就是现成的关系边，不需要从零做实体抽取。**先拿双链当图谱用，再对比 LLM 自动抽取的质量**——这个对照实验本身就是很好的 portfolio 素材。
