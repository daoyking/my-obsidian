# 人机协同（Human-in-the-loop）

## 定义

Agent 在执行过程中**主动暂停、把决策权交回人**的机制，而不是跑到底再让人看结果。三个动作构成闭环：Agent 发起 interrupt → 人做出选择/修正 → Agent 带着人的输入继续。

## 在 Agent 系统中的位置

- 与 [[Agent安全]] 的关系：HITL 是**最有效也最便宜**的一道护栏。高风险动作（付款、发邮件、删数据）与其靠模型自己判断，不如设计为必须人工确认。
- 与 [[常驻Agent]] 的关系：常驻 Agent 的「什么时候打扰人」本身就是 HITL 的反面问题——不是「Agent 停下来问人」，而是「Agent 判断这件事值不值得让人停下手头工作」。
- 与 [[Agent评估]] 的关系：HITL 产生的人的修正数据是极高质量的偏好信号，可回流做评估与微调。

## 协议层面的支持

[[AG-UI]] 把 HITL 写进了一等公民位置，而不是留给业务层 hack：

- `RUN_FINISHED` 的 `outcome` 字段支持 `{ type: "interrupt", interrupts: [...] }`
- 客户端通过**新一次 run 的 `resume` 数组**响应，Agent 从中断点继续
- `SUBAGENT_FINISHED` 的 `outcome` 支持 `{ type: "suspended", interruptIds: [...] }`，粒度到子代理

这带来一个工程上的关键区别：**中断不是错误**。`RUN_ERROR` 是不可恢复终止，之后不再有该 run 的事件；而 interrupt 是一次正常的、可续传的暂停。前端要能区分二者——前者显示失败，后者显示待确认卡片。

## UI 形态

| 形态 | 适用场景 |
|---|---|
| 审批卡（确认/拒绝） | 高风险动作前的闸门 |
| 选择卡（多个方案择一） | Agent 不确定偏好，如行程方案 |
| 可编辑的中间产物 | 计划/草稿，人直接改（如 deep research 的 todo 列表） |
| 静默默认 + 超时通过 | 低风险高频动作，避免打扰疲劳 |

`ai-deep-research-agent` 的 `write_todos` 是可编辑中间产物的典型：计划渲染成 todo 列表，人可以改，Agent 按改后的计划继续。

## 我的观点

- HITL 的设计难点不在实现，而在**阈值**：问太多人烦（打扰疲劳，最终变成无脑点确认，护栏形同虚设），问太少出事故。这个阈值应该随动作风险、Agent 历史准确率、人的在场状态动态调整，而不是写死。
- UI 是 HITL 的一部分而非附属品：一张信息不全的审批卡，等价于没设护栏——人只能盲签。**「让人看得懂再决定」是前端工程师在 Agent 安全里的独特贡献。**
