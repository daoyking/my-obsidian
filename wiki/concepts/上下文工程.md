# 上下文工程

## 定义

系统设计与管理喂给 LLM 的上下文（系统提示、对话历史、工具结果、检索内容、状态信息），以最大化 Agent 能力上限。上下文是 Agent 的「眼睛」——决定模型此刻能看到什么、能推理什么。

## 为什么重要

- 《AI Agents in Depth》称上下文工程是全书最关键的一章：**Agent 的能力上限由上下文决定，不是模型本身**
- 同一模型，好上下文与差上下文效果天差地别
- 是 [[Harness工程]] 的核心组成

## 核心机制

来自 [[raw/papers/ai-agents-in-depth]] 第 2 章：

1. **API 上下文结构**：消息四种角色（system/user/assistant/tool），单轮与带工具的多轮
2. **KV Cache 友好设计**：上下文布局影响缓存命中率，进而影响延迟与成本；Prompt Cache 与 KV Cache 是两个层级
3. **提示工程**：人格（语气风格）、结构化提示、流程驱动 vs 规则堆砌、Few-shot、工具定义设计
4. **提示注入防御**：见 [[提示注入]]
5. **Agent Skills**：领域能力的可组合单元，按需加载（见本库 Skill 机制）
6. **Agent 状态栏**：用元信息增强轨迹管理（位置、时间感知）
7. **上下文压缩**：分层压缩；**子 Agent 上下文隔离优于压缩**

## 关键洞见

- 「隔离优于压缩」：把子任务交给独立子 Agent（隔离上下文）比在主上下文里压缩更有效——这正是本知识库 Ingest 时「一个来源交给 AI 单独编译」的理论依据
- 上下文学习的内部机制是**检索而非推理**——所以压缩要保留可检索的结构

## 与本知识库的关联

- 本库的 [[CLAUDE]]（Schema）就是上下文工程产物：告诉接入的 AI 如何看待这个 vault
- Ingest/Lint 流程是「把对的上下文在对的时机喂给模型」
